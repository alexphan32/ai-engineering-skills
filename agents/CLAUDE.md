# Agent Ecosystem — Responsibility Framework

## SKILL vs AGENT: Division of Responsibility

| Concern | SKILL | AGENT |
|---------|-------|-------|
| Workflow steps (how-to) | ✅ Full detail | ❌ Only references "follow N steps" |
| Domain knowledge | ✅ Commands, formulas, constants | ❌ |
| Tool scope (allowed_prompts) | ❌ | ✅ |
| Approval gates | Pattern in SKILL | Concrete implementation in AGENT |
| Project-specific mappings | ❌ | ✅ Module→file mappings, enum paths |
| Output format templates | ✅ Detailed templates | Only if AGENT has its own format |
| Hard constraints | Pattern in SKILL | ✅ Project-specific hard rules |
| Trigger conditions | description field | description field |

**Rule**: If the content is about "how to do it" → put it in the SKILL. If it's about "who does what, when to ask the user, which tool to use" → put it in the AGENT.

## Agent Inventory

One generic, stack-agnostic agent per top-level skill in `skills/` — mirrors the lifecycle chain
documented in the repo root `CLAUDE.md` and `brainstorming/SKILL.md`. Each agent is an
**executor** for its skill (or, for `review-agent`/`brainstorming-agent`, a **router**) — it adds
tool scope and approval gates on top of the skill's own workflow, never re-documents the workflow
itself.

| Agent | Skill | Purpose |
|-------|-------|---------|
| `discovery-agent` | `discovery` | Context-gathering pass before routing to another skill — does NOT touch code |
| `spec-agent` | `spec` | Create/update SRS documents (MODE A: pipeline/script, MODE B: backend/frontend/mobile feature) |
| `design-agent` | `design` | Create SDS documents from an SRS — 12 modes (REST/full-stack API + Client UI) |
| `implement-agent` | `implement` | Implement 1 task per a plan/SDS — IMPLEMENT→TEST→VERIFY |
| `test-agent` | `test` | Test coverage beyond the inline unit loop — integration/contract/e2e/performance/concurrency/failure |
| `review-agent` | `review` | Router → `review` (CODE/SDS auto-detected internally) or `architecture` (UPGRADE mode) |
| `operate-agent` | `operate` | Deployment plan, observability, reliability, incident response, disaster recovery |
| `architecture-agent` | `architecture` | EXPLORE (document) / SELECT (choose) / UPGRADE (re-evaluate) architecture — does NOT touch src/ |
| `research-agent` | `research` | Multi-source web research — fact-check, technology evaluation |
| `brainstorming-agent` | `brainstorming` | Router for the whole lifecycle — classifies ceremony tier (Spike/Bounded/Architectural), routes to other agents |
| `insights-agent` | `insights` | Analyzes session transcripts (batch, any stack) → knowledge base |

**Routers vs. executors:** `review-agent` and `brainstorming-agent` never perform the underlying
work themselves — they detect and delegate. All other agents above execute their skill's workflow
directly. `review-agent` routes only between the `review` skill (which detects CODE vs. SDS mode
internally, the same way `design-agent` doesn't pre-detect stack) and `architecture` UPGRADE mode
for whole-system/topology requests.
